Understanding the Output

📊 Hit Rate Chart (Line Graph)

What it shows: How hit rate changes with block size

Key patterns:

  • Sequential: Steep rise → hit rate increases with block size (blocks capture more useful data)
  • Random: Flat or declining → block size doesn't help (data scattered)
  • Streaming: Moderate rise → prefetch hides misses efficiently

Target: > 90% for download workloads

⏱️ Average Access Time (AAT)

Formula: AAT = Hit Time + (Miss Rate × Miss Penalty)

Key insight: Miss penalty INCREASES with block size (takes longer to fill)

Example (64-byte block @ 8 GB/s):

Fill time = 64 bytes / (8 GB/s) = 8 ns ≈ 24 cycles @ 3GHz Miss penalty ≈ 26 cycles (tag latency + fill + delivery) With larger blocks (256 bytes): Fill time = 256 bytes / (8 GB/s) = 32 ns ≈ 96 cycles @ 3GHz Miss penalty ≈ 98 cycles (much longer!) AAT tradeoff: Larger block → fewer misses but longer penalty

🚌 Memory Bus Utilization

Definition: Fraction of fetched bytes actually used

Formula: Utilization = (Used Bytes / Block Size) × 100%

Examples:

Sequential access: 100% useful (every byte in block accessed) Random access: ~40% useful (only 1 access per block, rest unused) Larger blocks = lower utilization on random workloads = wasted memory bandwidth = wasted power

Target: > 80% (avoid excessive pollution)

📈 Download Throughput (GB/s)

Definition: File data per second (practical measure of performance)

Formula: Throughput = Hit Rate × Bus Bandwidth × Utilization

Example:

64-byte block, sequential workload: Hit Rate: 90%, Utilization: 95%, Bus: 8 GB/s Throughput = 0.90 × 8 × 0.95 = 6.84 GB/s ✓ Excellent 128-byte block, random workload: Hit Rate: 55%, Utilization: 40%, Bus: 8 GB/s Throughput = 0.55 × 8 × 0.40 = 1.76 GB/s ✗ Poor

Key insight: Sequential = prefer larger blocks; Random = smaller blocks

⏱️ Cache Block Fill Time

Definition: Time to transfer one block from memory to cache

Formula: Fill Time = (Block Size × 8 bits/byte) / Bandwidth

Examples:

@ 8 GB/s bus: 16 bytes: 16 ns = 48 cycles @ 3GHz 64 bytes: 64 ns = 192 cycles (but hide with prefetch) 256 bytes: 256 ns = 768 cycles (risky—blocks for too long) Target: Fill time < 20-30 cycles (CPU prefetch window)

🔬 Key Concepts Explained

Spatial Locality & Block Size

Principle: Large blocks exploit spatial locality—if A accessed, nearby addresses likely accessed soon

Sequential Access: Perfect spatial locality. Larger blocks amortize miss penalty over many useful hits.

Random Access: No spatial locality. Larger blocks fetch useless data → cache pollution

Real Workloads: Mix of both. Block size is compromise.

Cache Pollution

Definition

Fetching useless data that evicts hot (frequently used) data from cache

Example: Random Database Scan

Miss at Address A → Fetch 256-byte block (A to A+255) But only address A is accessed (1 byte used, 255 wasted) Block fills cache lines → evicts other hot pages Later miss at Address B triggers another 256-byte fetch Result: Cache full of pollution → thrashing → many misses

Solution

Smaller block size → less pollution → better for random workloads

Miss Penalty vs Block Size

📊 The Tradeoff Curve

Large Blocks:

  • ✅ Lower miss count (better spatial locality)
  • ❌ Higher miss penalty (longer fill time)
  • ❌ More cache pollution
  • ❌ More memory bus traffic (power)

Small Blocks:

  • ❌ Higher miss count (poor spatial locality)
  • ✅ Lower miss penalty (quick fill)
  • ✅ Less cache pollution
  • ✅ Less memory bus traffic

Optimal Size: Where product of (miss rate) × (miss penalty) is minimized

  • Calculate: Wasted bytes = (Block Size - 1) × Number of Misses

⚠️ Common Issues & Troubleshooting

❌ "Hit rate decreases with larger block size"

Cause: Random access pattern—larger blocks cause cache pollution

Solution: Try "Sequential" workload to see expected behavior

❌ "All block sizes show same throughput"

Cause: Other factors dominating (maybe cache already full)

Solution: Use smaller cache (16 KB) to amplify block size effects

❌ "AAT increases with larger blocks"

Cause: Correct! Longer fill times outweigh hit rate gains

Lesson: Larger block ≠ always faster. Tradeoff depends on workload.

❌ "Bus utilization drops to 40% on random workload"

Cause: Correct—random access doesn't benefit from large blocks

Lesson: 60% wasted bandwidth = 60% wasted power on random patterns

📚 Extended Reading

  • Spatial Locality: Programs access nearby memory addresses within short time
  • Prefetching: Hardware speculatively fetches next blocks to hide latency
  • Memory Bus: Shared link between CPU/cache and main memory—bandwidth limited
  • Cache Coherence: Multi-core systems need protocols (MESI) to maintain consistency
  • Streaming Workloads: Sequential access patterns (video, compression, databases)
  • Power Wall: Memory bandwidth scales with power—block size impacts energy
