🚀 Quick Start (5 Steps)

1

Open the Simulator

Launch Project3_ALU_Simulator.html in your web browser. You'll see:

  • Control panel with test case dropdown
  • ALU Pipeline Status (3 ALU units: Fast, Multiplier, Divider)
  • Instruction Queue showing upcoming operations
  • Execution trace log with detailed cycle information
  • Performance metrics including IPC, ALU Utilization, Power Efficiency
  • Operation Mix Analysis table
2

Select a Test Case

Choose from 4 audio DSP instruction mixes:

Test 1: Fast Operations Only
100% ADD/SUB/AND/OR/XOR/SHL/SHR (1-cycle operations)
→ Best case: high throughput, no stalls

Test 2: Multiplier Bottleneck
70% fast ops + 30% MUL (4-cycle operations)
→ Moderate case: some stalls waiting for multiplier

Test 3: Division Heavy (Worst Case)
50% fast + 40% MUL + 10% DIV (20-cycle operations)
→ Worst case: severe pipeline stalls

Test 4: Realistic Audio Processing
60% ADD/SUB + 25% MUL + 10% DIV + 5% bitwise
→ Real DSP algorithm mix
3

Load the Simulator

Click "Load Simulator". This initializes:

  • 3 ALU units (Fast, Multiplier, Divider) all idle
  • 100-instruction sequence based on test case
  • All metrics reset to zero
  • Execution trace log cleared
4

Execute Instructions

Two execution modes:

  • Step Forward ⏭️ - Execute one instruction at a time (detailed analysis)
  • Auto Run ▶️ - Execute all instructions automatically (300ms per step)
Pro Tip: Use Step Forward to observe how long-latency operations (MUL, DIV) create stalls and block other instructions.
5

Analyze Performance

Review key metrics:

  • Total Cycles: How many CPU cycles to execute all instructions
  • IPC (Instructions Per Cycle): Throughput (higher = better)
  • Stall Cycles: Wasted cycles waiting for ALU results
  • ALU Utilization: % of cycles where ALU is doing useful work
  • Power Efficiency: Operations per unit power (important for audio devices)
  • Real-Time Feasible: Can process in < 333 cycles @ 48kHz?

📊 Understanding the Display Panels

ALU Pipeline Status Table

Shows 3 separate ALU units:
  • Fast ALU: Handles ADD, SUB, AND, OR, XOR, SHL, SHR (1-cycle latency)
  • Multiplier Unit: Handles MUL (4-cycle latency)
  • Divider Unit: Handles DIV (20-cycle latency)
Status Colors: Green = Idle, Red = Busy
Why 3 units? Real CPUs have separate functional units to enable parallel execution
Example:
Fast ALU: Idle —
Multiplier: Busy (MUL, 3 cycles left)
Divider: Idle —
The multiplier is busy with a MUL operation, but the Fast ALU is free to execute ADD/SUB operations in parallel!

Instruction Queue

Shows: Next 8 instructions waiting to be executed
Color coding: First instruction (red) is currently executing
Why it matters: Helps visualize instruction dependencies and bottlenecks
Example:
[MUL] ← Currently executing (4-cycle latency)
[ADD]
[SUB]
[MUL] ← May stall waiting for previous MUL

Execution Trace Log

Shows: Cycle-by-cycle execution details
Key events logged:
  • Operation execution: which ALU unit, latency
  • Stalls: when instruction must wait for ALU
  • Completions: when operation finishes
Example Log Entries:
[C3] Execute MUL on multiplier ALU (latency: 4 cycles)
[C4] Execute ADD on fast ALU (latency: 1 cycle) ← Parallel execution!
[C4] Complete: ADD from fast ALU
[C5] STALL: MUL waiting for multiplier ALU (queue: 1)

Operation Mix Analysis

Shows: Breakdown of which operations were executed and their costs
Columns: Operation type, Count, Average latency, Total time consumed, % of total execution time
Why it matters: Identifies which operations are bottlenecks
Example (Test 3: Division Heavy):
ADD: 50 ops × 1 cycle = 50 cycles (25% of time)
MUL: 40 ops × 4 cycles = 160 cycles (60% of time) ← Bottleneck!
DIV: 10 ops × 20 cycles = 200 cycles (90% of time) ← Major bottleneck!
Even though DIV is only 10% of instructions, it consumes 90% of execution time!

🔍 Key Observations to Record

For Each Test Case, Answer:

  1. Which operation caused the most stalls? (MUL or DIV?)
  2. What is the theoretical minimum cycles? (If operations could overlap perfectly)
  3. What is the IPC? (Actual instructions executed per cycle)
  4. Is the processor real-time capable? (< 333 cycles @ 48kHz)
  5. How much is performance lost to stalls? (Stall cycles / Total cycles %)
  6. Could instruction reordering help? (Move ADD/SUB before stalled MUL/DIV)

Total Cycles: 285
Instructions: 100
Stall Cycles: 145
IPC: 0.35
ALU Utilization: 49%
Bottleneck: DIV (20-cycle latency)
Stall Loss: 51% of time wasted waiting

⚡ How ALU Pipelining Works

Sequential Execution (Without Parallelism):

Cycle 1: MUL (4 cycles)
Cycle 5: ADD (1 cycle)
Cycle 6: SUB (1 cycle)
Total: 6 cycles for 3 instructions

Parallel Execution (With Multiple ALUs):

Cycle 1: MUL on Multiplier (4 cycles)
Cycle 1: ADD on Fast ALU (same cycle!)
Cycle 2: SUB on Fast ALU (same cycle!)
Total: 4 cycles for 3 instructions ← 33% faster!
Key Insight: When you have separate ALU units (Fast, Multiplier, Divider), independent instructions can execute in parallel. The simulator shows this by allowing ADD/SUB to execute while MUL/DIV is working.
