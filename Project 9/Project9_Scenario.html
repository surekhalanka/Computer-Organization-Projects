📋 Project Overview

In this project, you'll design and optimize the CPU register file—the fastest on-chip storage that feeds data to execution units. You'll study how multiple read/write ports enable parallel processing, analyze forwarding logic to avoid data hazards, and measure performance on vectorized workloads. The goal is to understand the register file as the bottleneck in parallel execution and optimize its bandwidth, latency, and power.

🎯 Real-World Scenario

CloudCompute Inc: Parallel Fluid Dynamics Simulation

Background: CloudCompute operates a high-performance computing (HPC) cluster solving 3D fluid dynamics (CFD) for automotive aerodynamics. Each simulation kernel processes 1,024 grid points in parallel, requiring 4 simultaneous data read operations and 2 simultaneous writes per cycle. The CPU's register file must deliver 4 read ports (64 bytes/cycle) and 2 write ports (64 bytes/cycle) at 3 GHz. With 256 registers × 64-bit, the register file is heavily contested—forwarding logic must resolve data hazards (RAW, WAW, WAR) in <1 cycle or pipeline stalls.

Performance Requirements:

  • Read Ports: 4 simultaneous 64-bit reads per cycle (256 GB/s @ 3 GHz)
  • Write Ports: 2 simultaneous 64-bit writes per cycle
  • Register Count: 256 × 64-bit = 16 KB total
  • Hazard Detection: < 1-cycle latency (forwarding must hide hazards)
  • Forwarding Accuracy: > 99% correct data bypass
  • Pipeline Stall Rate: < 5% (avoid bubble insertion)
  • Parallel Throughput: 4 FMA ops/cycle (256 GFLOPS @ 3 GHz)
  • Power Budget: Register file + forwarding < 5W

⚙️ Register File Architecture

Register File Organization

Capacity: 256 registers × 64 bits = 16 KB (all on-die, 0-cycle access)

Port Configuration:

  • 4 Read Ports (R1, R2, R3, R4): Fetch 4 operands per cycle (e.g., Rs1, Rs2, Rs3, Rs4)
  • 2 Write Ports (W1, W2): Write 2 results per cycle (e.g., ALU result, FMA result)
  • Access Latency: 0 cycles (combinational logic, no wait)
  • Read Latency: 1 cycle (from register selection to data out)
  • Write Latency: 1 cycle (from write enable to register update)

Data Hazards in Pipeline

RAW (Read-After-Write) Hazard

Problem: Instruction I+1 reads R1 that I just wrote

Cycle 1: ADD R1, R2, R3 (Writes R1 @ end of cycle) Cycle 2: MUL R4, R1, R5 (Reads R1 @ start of cycle) ← R1 not updated yet!

Solution: Forwarding (bypass R1 from ALU output directly to MUL input)

Cost: Extra mux, if forwarding fails → 1-cycle stall

WAW (Write-After-Write) Hazard

Problem: Two instructions both write same register, out-of-order execution

Cycle 1: ADD R1, R2, R3 (Will write R1) Cycle 2: SUB R1, R4, R5 (Writes R1) ← Which value wins?

Solution: In-order commit (track write order) or register rename

WAR (Write-After-Read) Hazard

Problem: Instruction I+1 overwrites R1 that I still reading

Cycle 1: MUL R4, R1, R2 (Reads R1) Cycle 2: ADD R1, R3, R4 (Writes R1) ← Overwrites R1 being used!

Solution: Register rename (allocate new physical register)

Forwarding Network

Bypass Logic (1-Cycle Forwarding)

  • ALU→ALU Forwarding: ALU result (R1) → bypass to MUL input
  • ALU→FMA Forwarding: ALU result → FMA (floating-point multiply-add) input
  • FMA→ALU Forwarding: FMA result → ALU input (less common, extra latency)
  • Load→ALU Forwarding: Load result from L1 cache → ALU

Latency: Forwarding happens in 1 cycle (combinational), no pipeline stall

Coverage: Target: > 99% of RAW hazards resolved by forwarding

Hazard Detection Unit

Logic: Check if Rd_current matches Rw_previous (1 cycle back)

IF: Decode reads Rd1, Rd2, Rd3, Rd4 EX: Previous instruction wrote Rw If Rd_i == Rw → Hazard! Stall or forward? Forward if: - Result available from previous cycle (ALU/FMA latency = 1) - Source is not memory (load latency = 3+ cycles) Stall if: - Result comes from load (need L1 latency) - Complex dependencies

📊 Parallel Data Processing Workloads

Test Case 1: Sequential Scalar Processing (Baseline)

Workload: Scalar operations (1 result per cycle)

Example: FOR i=0 to 1000: R1 = R1 + R2 * R3

Register Usage: R1, R2, R3 only (3 of 256 registers)

Read Ports Used: 2 (R2, R3)

Write Ports Used: 1 (R1)

Hazards: RAW every cycle (R1 = ... R1)

Expected Results:

  • Port Utilization: 50% (2/4 read, 1/2 write)
  • Forwarding Coverage: 100% (R1→R1 always forwarded)
  • Stall Rate: ~0% (forwarding catches all RAW hazards)

Test Case 2: Vectorized Parallel (SIMD)

Workload: 4× parallel FMA operations per cycle

Example: [R1, R5, R9, R13] += [R2, R6, R10, R14] * [R3, R7, R11, R15]

Register Usage: 12 registers (3 sets of 4)

Read Ports Used: 4 (full bandwidth: R2, R3, R6, R7)

Write Ports Used: 2 (R1, R5; R9, R13 queued)

Hazards: Low (different registers, no conflicts)

Expected Results:

  • Port Utilization: 100% (4/4 read, 2/2 write)
  • Forwarding Coverage: 90% (only between adjacent FMAs)
  • Stall Rate: ~2% (occasional WAW on write port contention)
  • Throughput: 4 FMA ops/cycle = 256 GFLOPS @ 3 GHz

Test Case 3: Mixed Integer + FP Operations

Workload: 2× ALU operations + 2× FMA operations per cycle

Example: ALU: R1 = R2 + R3; ALU: R4 = R5 & R6; FMA: R7 = R8 * R9 + R10; FMA: R11 = R12 * R13 + R14

Register Usage: 14 registers (diverse types)

Read Ports Used: 4 (R2, R3, R5, R6 from ALU; R8, R9, R10, R12, R13, R14 from FMA—muxed)

Write Ports Used: 2 (R1, R4 from ALU; R7, R11 from FMA—can't both write)

Hazards: Moderate (ALU→FMA forwarding needed)

Expected Results:

  • Port Utilization: 80% (write port contention between ALU/FMA)
  • Forwarding Coverage: 85% (ALU→FMA slower due to pipeline depth)
  • Stall Rate: ~5% (occasional wait for write port)
  • Throughput: 3.8 ops/cycle (not quite 4 due to port contention)

Test Case 4: Load-Heavy Workload (Bandwidth Stress)

Workload: 4× load operations reading memory into 4 different registers

Example: R1 = MEM[R17]; R2 = MEM[R18]; R3 = MEM[R19]; R4 = MEM[R20]

Register Usage: 24 registers (4 destinations + 4 base pointers + other temps)

Read Ports Used: 4 (R17, R18, R19, R20)

Write Ports Used: 2 (R1, R2 from L1; R3, R4 queued next cycle)

Hazards: Load→ALU dependencies (3-cycle load latency)

Expected Results:

  • Port Utilization: 100% read, 50% write (loads don't need ALU)
  • Forwarding Coverage: 50% (load latency > 1 cycle, can't bypass)
  • Stall Rate: ~15% (wait for loads to complete from L1)
  • Throughput: ~1.7 ops/cycle (limited by load latency, not register file)

Test Case 5: Complex Dependencies (Stress Test)

Workload: Chain of dependent operations with frequent forwarding

Example: R1 = R2 + R3; R4 = R1 * R5; R6 = R4 - R1; R7 = R6 & R8 (each uses previous result)

Register Usage: 8 registers (sequential dependencies)

Read Ports Used: 2-4 per cycle (varying)

Write Ports Used: 1-2 per cycle

Hazards: HIGH (R1→R4→R6→R7 chains)

Expected Results:

  • Port Utilization: 30% (underutilized due to dependencies)
  • Forwarding Coverage: 95% (most forwarded, some stalls)
  • Stall Rate: ~20% (RAW hazards block execution)
  • Throughput: 0.8 ops/cycle (highly serialized)

📈 Performance & Design Metrics

Metric Definition Formula Target
Read Port Utilization (%) % of read ports active per cycle (Reads Used / Total Read Ports) × 100 > 75%
Write Port Utilization (%) % of write ports active per cycle (Writes Used / Total Write Ports) × 100 > 50%
Forwarding Coverage (%) % of RAW hazards resolved by bypass (Forwarded / Total RAW Hazards) × 100 > 99%
Stall Rate (%) % of cycles pipeline stalls (no progress) (Stall Cycles / Total Cycles) × 100 < 5%
Throughput (Ops/Cycle) Avg operations per cycle executed Total Ops / Total Cycles > 3.5 (of 4.0 max)
Register File Bandwidth (GB/s) Total data moved per second (Read_bytes + Write_bytes) × Clock_GHz > 200 GB/s
Register File Power (W) Power consumed by regfile + forwarding Dynamic + Leakage < 5W
Hazard Detection Latency (cy) Cycles to detect and resolve hazard Decode → Forwarding → Result < 1 cy

  • Understand register file organization (ports, access latency, capacity)
  • Recognize data hazards (RAW, WAW, WAR) and their effects
  • Design forwarding/bypass networks to hide latency
  • Analyze read/write port contention and bandwidth limits
  • Measure hazard detection latency and stall frequency
  • Optimize for parallel processing (vectorized workloads)
  • Estimate register file power consumption
  • Trade off port count vs area/power
  • Predict performance on mixed ALU/FMA/Load workloads
  • Apply knowledge to multi-threaded parallel programs
