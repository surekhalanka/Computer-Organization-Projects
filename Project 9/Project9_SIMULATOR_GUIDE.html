📖 Core Concepts

1. Register File Architecture

Basics

  • Size: 256 × 64-bit = 16 KB (all on-die, fastest storage)
  • Access Latency: 0 cycles (combinational—no wait)
  • Read Latency: 1 cycle (address → output)
  • Write Latency: 1 cycle (write enable → register update)

Port Configuration

Read Ports: How many simultaneous 64-bit reads per cycle?

  • 2 ports: Dual-issue processor, limited parallelism
  • 4 ports (standard): Quad-issue (e.g., 2 ALU + 2 FMA)
  • 6 ports (aggressive): Superscalar—multiple fetch/execute

Write Ports: How many simultaneous 64-bit writes per cycle?

  • 1 port: Only one result committed per cycle (narrow)
  • 2 ports (standard): ALU result + FMA result (balanced)
  • 4 ports (aggressive): Multiple ALU/FMA results (wide)

Bandwidth Calculation

Read Bandwidth = (Read Ports Used × 64 bits × Clock Rate) Example: 4 reads × 64 bits × 3 GHz = 768 Gbps = 96 GB/s Write Bandwidth = (Write Ports Used × 64 bits × Clock Rate) Example: 2 writes × 64 bits × 3 GHz = 384 Gbps = 48 GB/s Total BW = Read BW + Write BW Example: 96 + 48 = 144 GB/s

2. Data Hazards in the Pipeline

RAW (Read-After-Write) Hazard

Problem: Instruction I+1 reads register that I just wrote to

Cycle 1: ADD R1, R2, R3 (Computes R1, writes to register @ end of cycle) Cycle 2: MUL R4, R1, R5 (Reads R1 @ start of cycle—TOO EARLY!) ↑ R1 not yet updated; gets stale value

Impact: Must stall 1 cycle OR use forwarding

Solution: Forwarding (bypass ALU output directly to MUL without waiting for register write)

Cost: 1-cycle latency hidden by bypass network

WAW (Write-After-Write) Hazard

Problem: Two instructions write same register, order matters

Cycle 1: ADD R1, R2, R3 (Schedules write to R1) Cycle 2: SUB R1, R4, R5 (Also writes R1) ↑ Out-of-order execution: which value should R1 have?

Impact: Incorrect final value if SUB completes before ADD writes

Solution: In-order commit or register renaming (allocate R1' for SUB)

Cost: Requires physical register pool (>256 registers needed)

WAR (Write-After-Read) Hazard

Problem: Instruction I+1 overwrites register that I still needs

Cycle 1: MUL R4, R1, R2 (Reads R1 in pipeline) Cycle 2: ADD R1, R3, R4 (Overwrites R1—destroys value I still needs!) ↑ R1 needed in cycle 3 by MUL, but ADD destroys it

Impact: Lost data; MUL gets wrong value

Solution: Register rename (MUL reads R1_old, ADD writes R1_new)

Cost: Rename table management, physical registers

3. Forwarding (Bypass) Networks

What is Forwarding?

Idea: Instead of waiting for result to be written to register, send it directly to next instruction's input.

Normal path (with stall): ADD R1, R2, R3 → Write R1 to register (cycle end) → Stall 1 cycle MUL R4, R1, R5 → Read R1 from register (cycle start) Forwarding path (no stall): ADD R1, R2, R3 → Bypass result to MUL input (same cycle or next) MUL R4, R1, R5 → Use forwarded value immediately

Forwarding Paths (Common)

  • ALU→ALU: ADD result → next ADD input (1-cycle forward)
  • ALU→FMA: ADD result → FMA input (might be 2+ cycles due to depth)
  • FMA→ALU: FMA result → ALU input (rarely forwarded; high latency)
  • Load→ALU: Load result from L1 → ALU (3+ cycle latency, can't bypass)

Forwarding Coverage Metric

Forwarding Coverage % = (Hazards Resolved by Forward / Total Hazards) × 100 Example: RAW hazards: 950 Forwarded: 950 Stalled: 0 Coverage = 950/950 = 100% (perfect!) Example 2: RAW hazards: 1000 Forwarded: 800 (forward works) Stalled: 200 (forward can't help, e.g., load latency) Coverage = 800/1000 = 80%

Target Coverage: > 99% (minimize stalls)

4. Hazard Detection Unit

Detection Logic

IF Stage: Decode instruction, extract read registers Rd1, Rd2, Rd3, Rd4 EX Stage: Previous instruction wrote to register Rw Hazard detection: For each Rd_i: IF Rd_i == Rw → Hazard detected! → Can forward if (result ready) → Must stall if (result not ready, e.g., load, divide)

Latency of Hazard Detection

Target: < 1 cycle (combinational logic)

Delay path: Decode → Register address comparison → Forwarding mux → Result to ALU input

Path length: ~200 ps (negligible at 3 GHz = 333 ps per cycle)

Detection Statistics

What to measure:

  • Hazards detected per cycle (average)
  • Hazards resolved by forward vs stall
  • Latency of forward path (cycles)

5. Port Utilization & Bottlenecks

Read Port Contention

Problem: Need 4 operands but only 4 read ports

Ideal: R1 = R2 + R3; R4 = R5 * R6; R7 = R8 & R9; R10 = R11 | R12 (all parallel) Read ports needed: R2, R3, R5, R6, R8, R9, R11, R12 = 8 ports (NEED MORE!) Actual ports: 4 → Can only read 4 of 8 → Must stall some operations

Metric: Read Port Utilization = (Reads Used / Total Ports) × 100%

Target: > 75% (good utilization)

Write Port Contention

Problem: Multiple results ready to write same cycle, limited ports

Cycle N: 2 ALU results ready to write (R1, R2) 2 FMA results ready to write (R3, R4) Total: 4 writes needed, but only 2 write ports → 2 writes queued, executed next cycle

Metric: Write Port Utilization = (Writes Used / Total Ports) × 100%

Target: > 50% (reasonable given fewer results than reads)

Port Efficiency Calculation

Read Port Efficiency = (Avg Reads / Max Ports) × 100 Example: 2.5 avg / 4 max = 62.5% Write Port Efficiency = (Avg Writes / Max Ports) × 100 Example: 1.2 avg / 2 max = 60% Total Bandwidth Efficiency = (Total Bytes / Max Bandwidth) × 100 Max Bandwidth = (4 reads + 2 writes) × 8 bytes × Clock = 48 × 3 = 144 GB/s Used: 90 GB/s → Efficiency = 90/144 = 62.5%

6. Throughput & Stalls

Throughput Definition

Throughput (ops/cycle): How many operations complete per cycle?

Throughput = Total Operations / Total Cycles Example: Total ops: 4000 Total cycles: 1200 (1000 ideal + 200 stalls) Throughput = 4000 / 1200 = 3.33 ops/cycle (out of max 4.0) IPC = 3.33 instructions/cycle

Stall Analysis

Stall Rate %: Fraction of cycles pipeline makes no progress

Stall Rate = (Stall Cycles / Total Cycles) × 100 Sources of stalls: 1. RAW hazard (forwarding can't reach in time) 2. WAW hazard (can't write same register twice/cycle) 3. Load latency (L1 miss, waiting for data) 4. Write port contention (too many results, limited ports) 5. Branch misprediction (recovery pipeline) Example: 1000 total cycles, 150 stall cycles Stall Rate = 150/1000 = 15% Performance Loss = 15% of 4 ops/cycle = 0.6 ops lost/cycle

Target Stall Rate: < 5% (most instructions make progress)

7. Register Renaming (Advanced)

Problem Without Renaming

Architectural registers: R0-R255 (limited, WAW hazards) Code: ADD R1, R2, R3 (I1 writes R1) SUB R1, R4, R5 (I2 writes R1, possible WAW) MUL R6, R1, R7 (I3 reads R1—should get I2's value, not I1's)

Solution: Physical Registers

Idea: Map architectural R1 to different physical registers per instruction

Architectural: ADD R1, R2, R3 → Physical: ADD P1, P2, P3 (P1 = physical register) SUB R1, R4, R5 → Physical: SUB P17, P4, P5 (P17 ≠ P1, new allocation) MUL R6, R1, R7 → Physical: MUL P18, P17, P7 (P18=result, P17=R1's latest) Rename table: R1 → P17 (latest physical register for R1)

Cost: More registers needed (e.g., 256 architectural → 512 physical)

Benefit: No WAW hazards, eliminates some stalls

When to use: Out-of-order execution, speculation

📊 Understanding Simulator Output

Port Utilization

Read Port Utilization: 100% → All 4 read ports used every cycle (maximum pressure)

Read Port Utilization: 75% → Average 3 of 4 ports active (good usage)

Read Port Utilization: 25% → Average 1 of 4 ports active (underutilized)

Interpretation:

  • High utilization = well-parallelized code, register file is bottleneck
  • Low utilization = insufficient parallelism or dependency chains

Forwarding Coverage

Forwarding Coverage: 100% → All RAW hazards resolved by bypass (no stalls from RAW)

Forwarding Coverage: 80% → 80% of RAW resolved, 20% require stall

Forwarding Coverage: 50% → Many hazards unresolvable (e.g., load latency)

Interpretation:

  • High coverage (>95%) = forwarding network effective
  • Low coverage (<70%) = workload has unpredictable latencies (loads, divides)

Stall Rate & Throughput

Stall Rate 0%, Throughput 4.0 ops/cycle: Perfect execution (all 4 ops/cycle)

Stall Rate 5%, Throughput 3.8 ops/cycle: Occasional hiccups (good performance)

Stall Rate 20%, Throughput 2.4 ops/cycle: Significant dependencies (needs optimization)

Formula: Throughput = (Total Ops) / (Ideal Cycles + Stall Cycles)

Hazard Counts

Hazard Type Example Impact (No Forwarding)
RAW (Read-After-Write) ADD R1; MUL R1 1 stall cycle (load use)
WAW (Write-After-Write) ADD R1; SUB R1 Order violation, wrong result
WAR (Write-After-Read) MUL R4,R1; ADD R1 Data lost, wrong computation

Power Analysis

Register File Power: Dynamic power (accesses) + Leakage

Baseline: ~1-3 W for typical 256×64-bit register file

High Utilization: Power increases with read/write frequency

Efficiency (Ops/Watt): Higher = better (more work per joule)

Example:

  • 4000 ops, 2.5 W power → 1,600 ops/watt (efficient)
  • 2000 ops, 3.0 W power → 667 ops/watt (wasteful)

💡 Tips & Troubleshooting

Maximizing Parallelism (High Throughput)

  • Unroll loops (expose more independent operations)
  • Increase register file read ports (4 → 6)
  • Vectorize code (SIMD: 1 op/cycle → 4 ops/cycle)
  • Reduce data dependencies (reorder operations)

Reducing Stalls

  • Enable hardware forwarding (catches most RAW hazards)
  • Prefetch data to hide load latency (3 cycles → 1 cycle effective)
  • Schedule independent operations between dependent ones (ILP)
  • Avoid back-to-back loads (L1 cache misses compound)

Common Mistakes

  • Ignoring write port contention: 4 results ready but only 2 write ports—causes queuing!
  • Assuming forwarding is free: Forwarding adds combinational delay; might not meet timing at high GHz.
  • Over-engineering register file: 6R + 4W is expensive (area, power). 4R + 2W usually sufficient.
  • Forgetting about load latency: L1 miss = 3+ cycles; can't forward → must stall or prefetch.

Real-World Optimization (CloudCompute CFD)

Problem: Vectorized workload only achieving 2.5 ops/cycle (target: 4.0)

Diagnosis: Write port contention (4 FMA results, 2 write ports)

Solution Steps:

  1. Increase write ports from 2 → 4 (extra area 15%)
  2. Throughput jumps to 3.8 ops/cycle
  3. Power increases by 0.8 W (acceptable)
  4. Performance gain: +52% (2.5 → 3.8)
  5. New design achieves 256 GFLOPS @ 3 GHz target ✓
