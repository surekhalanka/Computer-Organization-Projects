Understanding the Output

📊 Hit Rate Chart (Line Graph)

What it shows: How hit rate increases with cache size

Key pattern: Steep rise (small sizes) then flattens (large sizes) = diminishing returns

Reading it: Vertical axis = hit rate (0-100%), horizontal = cache size (4-256 KB)

Target: Aim for > 95% for video streaming

⏱️ Average Access Time (AAT) Chart

Formula: AAT = Hit Time + (Miss Rate × Miss Penalty)

Example: 90% hit rate → AAT = 1 + 0.10 × 100 = 11 cycles

Why it matters: Lower AAT = faster program execution

Target: < 5 cycles (near optimal)

💰 Performance/Area Efficiency

Definition: Hit rate per unit die area (mm²)

Formula: Efficiency = Hit Rate / Cache Area

Why important: Larger caches are exponentially more expensive to manufacture

Example:

32 KB: 90% hit rate / 14 mm² = 6.4% per mm² 64 KB: 95% hit rate / 26 mm² = 3.7% per mm² Verdict: 32 KB is MORE efficient (fewer mm² wasted)

⚡ Energy Efficiency (nJ/access)

Definition: Energy consumed per memory access

Formula: Energy = Power × AAT (in Joules at 3GHz)

Example:

4 KB cache: 0.5W × 21 cycles / 3GHz = 3.5 nJ/access 32 KB cache: 2.5W × 11 cycles / 3GHz = 9.2 nJ/access Target: < 20 nJ/access for streaming servers

Key insight: Larger cache uses more power, but fewer misses save time—tradeoff!

Identifying the "Knee Point"

💡 What is the Knee Point?

The cache size where diminishing returns begin—additional capacity provides minimal benefit.

How to spot it: In Hit Rate chart, look for where curve changes from steep to flat

The simulator marks it: "Knee Point (diminishing returns): 32 KB" means beyond 32 KB, hit rate gain is negligible

Business decision: Knee point = sweet spot: stop adding cache here

🔬 Key Concepts Explained

Capacity Misses vs. Conflict Misses

Capacity Misses

Definition: Working set exceeds cache capacity

Example: 10 MB video buffer with 8 MB cache → 20% capacity misses minimum

Solution: Increase cache size (this simulator's focus)

Limit: Even with infinite cache, can't eliminate if WS > cache

Conflict Misses

Definition: Multiple addresses compete for same cache location

Controlled by: Associativity (not size)

Note: This simulator uses 4-way default (mostly eliminates conflicts)

Working Set Theory

Principle: Programs use small subset of memory repeatedly (working set)

For video: Working set = current frame buffer + codec state (~10 MB for 4K)

Implication: Cache size should match working set size for optimal performance

Reality: WS > typical L1 cache → need L2/L3 hierarchy

🎯 Lab Experiments

Experiment 1: Single vs. Multi-Stream Scalability

Objective: Compare how different cache sizes handle workload scaling

Procedure:

  • Run: Single 4K Stream workload → record all hit rates
  • Run: Multi-Stream (16) workload → record all hit rates
  • Compare: How much additional cache needed for 16× workload?

Expected Result: Multi-stream requires ~3-4× larger cache (WS grows linearly)

Experiment 2: Finding Your Knee Point

Objective: Identify optimal cache size for your workload

Procedure:

  • Run simulation with your typical workload
  • Locate where Hit Rate chart flattens (simulator marks it)
  • Record cache size at knee point
  • Check Performance/Area ratio at that size

Expected Result: 32 KB for single stream, 64 KB for multi-stream

Experiment 3: Energy vs. Performance Tradeoff

Objective: Balance performance gains against power increase

Procedure:

  • Compare: 32 KB (baseline) vs 64 KB cache
  • Measure: AAT improvement, power increase, energy/access
  • Calculate: Is 5% AAT improvement worth 1.7W power increase?

Expected Result: 32 KB better value (diminishing returns at 64 KB)

⚠️ Common Issues & Troubleshooting

❌ "All cache sizes show same hit rate"

Cause: Working set fits in smallest cache (4 KB)

Solution: Try "Multi-Stream (16 concurrent)" workload

❌ "Hit rate doesn't reach 90%+ even with 256 KB"

Cause: Working set exceeds 256 MB (capacity miss limit)

Solution: This is expected! Cache can't exceed physics. Try "Single 4K Stream".

❌ "Energy chart shows larger cache uses more energy"

Cause: Correct! Larger cache = more power (even if AAT improves)

Lesson: Power budget may limit cache size despite performance gains

❌ "Charts don't update when I change settings"

Solution: Click "▶ Run Simulation" button after changing any setting

📚 Extended Reading

  • Amdahl's Law: Overall speedup limited by cache-bound portion
  • Working Set: Concept from Denning (1968)—subset of pages actively referenced
  • Page Fault: When working set accessed > cache capacity available
  • Scaling Laws: Cache area grows quadratically, but performance gain sublinear
  • Power-Performance: Larger cache = higher power, but hit rate improvement plateaus
  • Multi-Level Hierarchy: L1 (fast, small) + L2 (slower, large) balances tradeoffs
  • Memory Wall: CPU-memory gap grows → cache critical for performance
