📖 Core Concepts

1. Multiplexer Fundamentals

What is a Multiplexer?

Definition: Combinational logic that selects one of N inputs based on ⌈log₂(N)⌉ select signal bits.

2:1 Multiplexer (Simplest): Inputs: A, B Select: S (1 bit: 0 or 1) Output: Y = (S == 0) ? A : B S | Output 0 | A 1 | B 4:1 Multiplexer: Inputs: I0, I1, I2, I3 Select: S[1:0] (2 bits, 4 options) Output: Y = I[S] S1 S0 | Output 0 0 | I0 0 1 | I1 1 0 | I2 1 1 | I3 32:1 Multiplexer (Network Switch): Inputs: 32 input ports (each 64 bits wide) Select: S[4:0] (5 bits, 32 options) Output: Selected input port data

Multiplexer Characteristics

N:1 Mux Select Bits Implementation Latency Area (transistors)
2:1 1 Single AND-OR 2 gate delays ~6
4:1 2 2-level logic 3-4 gate delays ~24
8:1 3 3-level tree 5-6 gate delays ~60
32:1 5 5-level tree 10-15 gate delays ~300

Mux Implementation Strategies

Tree Structure: Cascaded stages of smaller muxes (area-efficient)

32:1 Mux as tree of 2:1 muxes: Input[0:1] → 2:1 Mux → L1_0 Input[2:3] → 2:1 Mux → L1_1 ... L1[0:1] → 2:1 Mux → L2_0 L1[2:3] → 2:1 Mux → L2_1 ... (Continue until single output) Latency: log₂(32) = 5 stages × ~2ns = 10 ns Area: 31 × 2:1 muxes (vs 1024 for flat implementation)

Flat Structure: Single-stage 32-input AND-OR network (faster, larger area)

32:1 Mux as flat AND-OR: For each input i (0-31): AND gate: Input[i] AND Decoder[i] All AND outputs feed into large OR gate Latency: 3 gate delays (fast!) Area: 32 decoders + 32 AND + 1 OR = expensive

2. Crossbar Switching Fabric

What is a Crossbar?

Definition: N×M grid of multiplexers allowing any input to connect to any output simultaneously (non-blocking)

32×32 Crossbar: Input Ports (0-31) │ │ │ ...│ └─┼─┼─────┘ │ │ ┌─┴─┴────────────────────┐ │ 32 × 32 Mux Array │ │ (1,024 total muxes) │ │ Each (i,j) can route │ │ input i to output j │ └─┬─┬────────────────────┘ │ │ Output Ports (0-31) │ │ │ ...│ Key Property: Any input can reach any output in same cycle (non-blocking) No contention between different input-output paths Maximum throughput = 32 inputs × 12.5 Gbps = 400 Gbps

Crossbar Variants

Single-Stage (Flat) Crossbar:

  • All connections in parallel (combinational logic)
  • Latency: Single mux delay (~10 ns)
  • Area: O(N²) muxes (expensive for large N)
  • Power: High dynamic (many muxes active)
  • Best for: Small switches (8-32 ports)

Multi-Stage (Hierarchical) Crossbar (Clos, Benes):

  • Decompose N×N into 3+ stages of smaller crossbars
  • Latency: ~3× higher (3 stages)
  • Area: O(N log N) muxes (more efficient)
  • Power: Lower than flat (fewer muxes per stage)
  • Blocking: Low but non-zero (multi-stage blocking)
  • Best for: Large switches (64+ ports)

3. Routing Algorithms & Load Balancing

Algorithm 1: Fixed Routing (Destination-Based)

Decision Process: Packet destination address → lookup table → output port

Packet header: [Dest MAC: 00:11:22:33:44:55] ↓ Lookup table: 00:11:22:* → Output port 5 ↓ Mux select: Port 5 (all packets to this destination use port 5)

Pros: Simple, predictable, fast lookup

Cons: No load balancing, creates hot spots

Latency: Lookup (10-20 ns) + Mux delay (10 ns) = ~25-30 ns per packet

Use case: Small LANs, deterministic networks (some HPC clusters)

Algorithm 2: Load-Balanced Routing (Adaptive)

Decision Process: Find least-loaded path among valid routes to destination

Packet destination: 192.168.1.0/24 (reachable via ports 5, 6, 7) ↓ Queue measurement: Port 5 queue: 500 bytes (heavy) Port 6 queue: 100 bytes (light) ← SELECT Port 7 queue: 300 bytes (medium) ↓ Mux select: Port 6 (least congested)

Pros: Balances load, reduces tail latency, prevents hot spots

Cons: More complex (need multiple routing entries), higher lookup latency

Latency: Routing + queue monitoring (20-30 ns) + Mux delay = ~35-40 ns

Use case: Data centers, cloud networks (DC fabric)

Algorithm 3: Hash-Based Routing (Flow-Consistent)

Decision Process: Hash packet 5-tuple (src IP, dest IP, src port, dest port, protocol) mod N

Packet 5-tuple: 10.0.0.1:12345 → 192.168.1.100:80 (TCP) ↓ Hash function: Hash(5-tuple) = 0x1A3F (some value) ↓ Modulo: 0x1A3F mod 32 = 7 ↓ Mux select: Port 7 (same port for all packets in this flow)

Pros: Fast (just hash), preserves packet order within flow, uniform if hash good

Cons: Uneven distribution with poor hash, can't adapt to congestion

Latency: Hash (5-10 ns) + Mux delay (10 ns) = ~15-20 ns (fastest!)

Use case: High-speed switches requiring packet ordering (lossless networks)

Algorithm 4: Multicast (Fan-Out)

Decision Process: Route packet to multiple output ports simultaneously

Multicast packet: [Dest group: 224.0.0.5 (all hosts)] ↓ Membership table: Group 224.0.0.5 → Ports {0, 2, 5, 7, 15, 18, ...} ↓ Mux select: Enable multiple output ports, replicate packet

Pros: Enables group communication, broadcast/multicast

Cons: High contention, replication overhead

Latency: Membership lookup (15-20 ns) + Replication logic (5 ns) = ~25 ns

Use case: Video distribution, cluster synchronization

4. Load Balance Metrics

Max-to-Average Ratio

Metric: How much more loaded is the hottest port compared to average?

Balance Ratio = Max Load / Avg Load Perfect balance (uniform): Ratio = 1.0 Good load distribution: Ratio < 1.2 Moderate imbalance: Ratio 1.2 - 2.0 Severe hot spot: Ratio > 2.0 Example: 32 ports, total 400 Gbps Avg per port: 400 / 32 = 12.5 Gbps Max load: 40 Gbps (4× average) Ratio: 40 / 12.5 = 3.2 (severe imbalance!)

Jain Fairness Index

Metric: 0 to 1 scale measuring fairness of bandwidth allocation

Jain Index = (Σ L_i)² / (N × Σ L_i²) Where: L_i = load on port i, N = number of ports Perfect fairness: Jain = 1.0 (all ports equal load) Good fairness: Jain > 0.95 Moderate fairness: Jain 0.8-0.95 Poor fairness: Jain < 0.8 Example: 4 ports with loads [12.5, 12.5, 12.5, 12.5] Gbps Sum: 50, Sum²: 2500 Jain = 2500 / (4 × 2500) = 1.0 (perfect) Example: 4 ports with loads [40, 0, 0, 0] Gbps Sum: 40, Sum²: 1600 Jain = 1600 / (4 × 1600) = 0.25 (terrible)

Output Queue Utilization

Metric: How full are output queues?

Queue depth % = (Bytes queued / Max queue size) × 100 Healthy: < 50% full (room for bursts) Concerning: 50-80% (traffic arriving faster than leaving) Critical: > 80% (will drop packets soon) Overflow: 100%+ (actively dropping packets)

5. Latency Components

Total Switch Latency = Routing Lookup + Mux Selection + Queue Wait

Total Latency = T_lookup + T_mux + T_queue T_lookup (Routing Lookup): 10-20 ns (CAM/TCAM table, depends on algorithm) Fixed routing: ~10-15 ns (simple hash) Adaptive routing: ~15-25 ns (complex decision) Hash-based: ~5-10 ns (fast hash) T_mux (Multiplexer Selection): 5-15 ns (depends on mux depth) Flat 32:1 mux: ~10 ns (single stage) Hierarchical: ~15-20 ns (3 stages × 5-7 ns) T_queue (Output Queue Wait): 0-1000s ns (depends on congestion) No congestion: ~0 ns (packet passes through) Light congestion: ~100-500 ns (typical) Heavy congestion: ~1-10 microseconds (queue buildup) Overflow: Packet dropped (∞ latency) Example calculations: Fixed routing, flat mux, no congestion: Latency = 12 ns + 10 ns + 0 ns = 22 ns = 0.022 μs ✓ Adaptive routing, multi-stage mux, moderate congestion: Latency = 20 ns + 18 ns + 500 ns = 538 ns = 0.538 μs ✓ Hierarchical routing with hot spot congestion: Latency = 15 ns + 20 ns + 5000 ns = 5.035 μs (5 microseconds queue wait dominates!)

6. Mux Power Consumption

Dynamic Power (Switching Activity)

Formula: P_dyn = α × C × V² × f

  • α: Activity factor (% of muxes switching)
  • C: Capacitance (~1 pF per 2:1 mux)
  • V: Voltage (0.8-1.0V modern)
  • f: Clock frequency (not always needed for combinational mux)
Example: 32×32 crossbar (1,024 muxes) Per mux switching: ~0.1 pJ (femtojoules) At 100% activity (all muxes active): 1,024 × 0.1 pJ = 102.4 pJ per cycle @ 3 GHz (333 ps/cycle): 102.4 pJ × 3 GHz = 0.31 W

Leakage Power (Static)

Formula: P_leak = I_leak × V

Leakage current increases exponentially with temperature. Typical ~10% of dynamic power.

Example: 32×32 crossbar (1,024 muxes × 0.2 μA leakage) I_leak = 1,024 × 0.2 μA = 204.8 μA @ 0.9V: P_leak = 204.8 μA × 0.9V = 0.18 W Total power (dynamic + static): 0.31 W + 0.18 W = 0.49 W ≈ 0.5 W per crossbar (Replicable for routing logic, buffer management, etc.)

Objective: Quantify performance loss from unbalanced traffic.

Procedure:

  3. Compare with Workload 1: Uniform Random
  4. Calculate: Performance ratio = Uniform Throughput / Hot-Spot Throughput

Expected Result: Hot spot case drops 75% of packets, only ~50 Gbps effective (8× worse!)

Experiment 2: Load-Balanced Routing Effectiveness

Procedure:

  3. Record throughput, packet loss, latency

Objective: Trade off latency vs area with different fabric topologies.

💡 Tips & Troubleshooting

Identifying Hot Spots

  • Check Max Load in output load table
  • High load ratio (Max/Avg > 2.0) indicates hot spots
  • Look for port numbers with Gbps >> average
  • Correlate with packet loss (hot ports = packet drops)

Optimizing Load Distribution

  • Use adaptive or hash-based routing (avoid fixed routing)
  • Increase number of valid paths to popular destinations
  • Consider multi-path routing (ECMP: Equal-Cost Multi-Path)
  • Monitor queue depths and rebalance if needed

Common Mistakes

  • Underestimating mux depth: 32:1 mux = 5-level tree, not single gate!
  • Ignoring multicast overhead: 10% multicast traffic ≠ 10% throughput reduction
  • Assuming single-stage always best: For 64+ ports, multi-stage more efficient
  • Forgetting queue delays: Mux selection is fast (~10 ns), but queue wait can be microseconds
  • Poor hash design: Bad hash function leads to hot spots despite hash-based routing

Real-World Optimization (NetFlow Corp)

Problem: 400 Gbps switch achieving only 50 Gbps throughput (hot spot)

Root Cause: Fixed routing sends 80% of traffic to single port

Solution Steps:

  1. Implement load-balanced routing → Throughput jumps to 160 Gbps
  2. Add more parallel paths to hot destination → Throughput → 320 Gbps
  3. Enable ECMP (4 equal-cost paths) → Throughput → 400 Gbps ✓
  4. Monitor for other hot spots and repeat

Result: Non-blocking fabric achieving full line rate throughput
