🚀 Quick Start (5 Steps)

1

Open the Simulator

Launch Project2_Register_Memory_Simulator.html in your web browser. You'll see:

  • Control panel at top
  • Two-column layout: Registers (left) & Memory (right)
  • Execution trace log below
  • Performance metrics at bottom
2

Select a Test Case

Choose one of 4 test cases from the dropdown:

Test 1: All Zeros - Best case, minimal hazards
Test 2: High Register Pressure - Worst case, max hazards
Test 3: Real File Data - ASCII text simulation
Test 4: Random Data - Realistic encryption workload
3

Load the Simulator

Click "Load Simulator" button. This initializes:

  • All 8 registers (R0-R7) to 0x00
  • Input memory block (0x1000-0x100F) with plaintext
  • Output memory block (0x2000-0x200F) empty
  • Execution trace log cleared
4

Execute Instructions

Two execution modes:

  • Step Forward ⏭️ - Execute one instruction at a time (best for detailed analysis)
  • Auto Run ▶️ - Execute all instructions automatically (500ms per step)
Pro Tip: Use Step Forward to carefully observe register hazards and memory access patterns.
5

Analyze Results

After execution, review the metrics:

  • Total Cycles: How many CPU cycles needed
  • Hazards Detected: How many RAW/WAR/WAW hazards occurred
  • Stall Cycles: Performance loss from hazards
  • Memory Operations: Total loads + stores
  • Cycles Per Block: Efficiency metric (lower = better)

📊 Understanding the Display Panels

Registers Panel (Left Side)

What you see: All 8 CPU registers (R0-R7) with their current values in hexadecimal
Color coding: Registers highlighted in light red indicate they're involved in a hazard
Example:
R0: 0x2B       ← Contains encryption key byte
R1: 0x7E       ← Part of round key
R2: 0xAB       ← Contains plaintext

Memory Watch Panel (Right Side)

Input Block (0x1000-0x100F): Original plaintext data being encrypted
Output Block (0x2000-0x200F): Ciphertext written during encryption
Color coding: White = unread, Blue = has been read, Green = has been written
Example:
0x1000: 43   ← 'C' from "CloudVault"
0x1001: 6C   ← 'l' (read during AES)
0x2000: 8A   ← Encrypted output

Execution Trace Log

Shows: Each instruction executed with cycle number, register/memory values, and operation description
Color coding: Red entries = hazard detection, Blue entries = memory operations
Example Log Entry:
[C4] RAW Hazard detected! SUB R3, R3, R0 (Stall: 2 cycles)
[C5] LOAD R2 from 0x1008 = 0x4C (Load plaintext)

Performance Metrics

Metric What It Means Target
Total Cycles CPU clock cycles to encrypt one 16-byte block < 70
Hazards Detected Number of RAW/WAR/WAW register conflicts found < 4
Stall Cycles Wasted cycles due to hazards (2 per RAW, 1 per WAR) < 8
Memory Operations Total LOAD + STORE instructions executed ~16-32
Registers Used How many of 8 registers were actively used 4-8
Cycles Per Block Total cycles for one 16-byte encryption < 70

🔍 Key Observations to Record

For Each Test Case, Answer:

  1. Register Hazards: How many RAW/WAR/WAW hazards occurred? Which registers were involved?
  2. Stall Overhead: How many cycles were wasted due to hazards? What % of total time?
  3. Memory Access Pattern: Were accesses sequential (cache-friendly) or random?
  4. Register Utilization: How many of 8 registers were needed? Could we use fewer?
  5. Performance Bottleneck: Is the limiting factor register hazards, memory latency, or instruction dependencies?
Example Data Collection:

Test 1 (All Zeros):
- Total Cycles: 52
- Hazards: 1
- Stall Cycles: 2
- CPB: 52.0
- Bottleneck: Memory access to 0x2000 (L1 cache miss)

📝 Common Patterns to Look For

1. Register-After-Write (RAW) Hazard

When an instruction reads from a register that was just written:

Cycle 3: LOAD R0 from 0x1000
Cycle 4: XOR R0, R0, R2 ← R0 not yet available!
Result: 2-cycle stall, 3 total cycles

2. Write-After-Read (WAR) Hazard

When a register is written before an earlier read completes:

Cycle 2: LOAD R1 from 0x1004
Cycle 3: SUB R1, R1, R0 ← Read still in progress
Result: 1-cycle stall

3. Cache Miss Pattern

When jumping from input block (0x1000) to output block (0x2000):

  • Sequential reads 0x1000-0x100F: ~100% L1 cache hit
  • Jump to 0x2000: L1 cache miss, ~50-cycle penalty
  • Sequential writes 0x2000-0x200F: ~100% hit again

⚠️ Troubleshooting

Simulator won't start: Make sure you've clicked "Load Simulator" before trying to step forward.
Values look wrong: Check that you selected the correct test case before loading. Different tests start with different plaintext values.
Need to restart: Click "Reset 🔄" to clear all values and start fresh with a different test case.
