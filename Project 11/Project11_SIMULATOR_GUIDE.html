  • Branch Accuracy: 80-99% (prediction hardware)

Click ▶ Run Simulation. The simulator calculates:

📖 Core Concepts

1. Cycles Per Instruction (CPI) Fundamentals

What is CPI?

Definition: Average number of clock cycles required to execute one instruction.

CPI = Total Cycles / Total Instructions Inverse: IPC (Instructions Per Cycle) = 1 / CPI Example: CPU: 3.5 GHz (3.5 × 10^9 cycles/second) Workload: 1 billion instructions @ CPI = 2.0 Time = 1,000,000,000 instr × 2.0 cycles/instr ÷ 3.5 × 10^9 cycles/sec = 2,000,000,000 cycles ÷ 3.5 × 10^9 cycles/sec = 0.571 seconds

Perfect vs Realistic CPI

Scenario CPI IPC Achievability
Perfect (no stalls) 1.0 1.0 Impossible (at least some overhead)
Good (minimal stalls) 0.8 - 1.2 0.83 - 1.25 Achievable with simple code, good cache
Fair (typical) 1.5 - 2.0 0.5 - 0.67 Realistic for mixed workloads
Poor (bottleneck) 2.0 - 4.0+ 0.25 - 0.5 Memory-bound, high branch misprediction
Superscalar (N-issue) 1/N N Theoretical max (rarely achieved)

The CPI Equation (Components)

CPI = Base CPI + RAW Hazard Stalls + Branch Mispred Stalls + Cache Miss Stalls Base CPI ≈ 1.0 (no stalls, but realistic due to pipeline stages) For N-issue superscalar: Base CPI ≈ 1/N (hard to achieve) RAW Stalls: Read-After-Write data dependency Example: load r1; add r2, r1, r3 → 1-2 cycle wait Impact: (% of instructions with deps) × (avg latency - 1) Branch Misprediction Stalls: Flush pipeline on wrong path prediction Impact: (branch rate) × (misprediction rate) × (pipeline depth) Example: 15% branches, 5% miss rate, 14 stages = 0.15 × 0.05 × 14 = 0.105 cycles/instr Cache Miss Stalls: L1 miss → L2: +6 cycles (10 - 4 = 6) L2 miss → L3: +30-50 cycles L3 miss → DRAM: +150-300 cycles Impact: (load rate) × (miss rate) × (penalty) Example: 20% loads, 5% L1 miss rate, 6 cycle penalty = 0.20 × 0.05 × 6 = 0.06 cycles/instr Total example: 1.0 + 0.08 (RAW) + 0.03 (branch) + 0.09 (L1) + 0.2 (L2) = 1.4 CPI

2. Pipeline Hazards & Stalls

Data Hazards (RAW - Read-After-Write)

Scenario: Instruction must wait for prior instruction's result

Pipeline stages: [IF] [ID] [EX] [MEM] [WB] Sequence (with 1-cycle FMA latency): Cycle 1: FMA r1, r2, r3 [IF] → [ID] → [EX] → [MEM] → [WB] (result ready at cycle 5) Cycle 2: (dep) [IF] → [ID] → [EX] (stall: waits for r1) Cycle 5: ADD r4, r1, r5 [ID] → [EX] → [MEM] → [WB] Stall: 3 cycles (cycles 2-4, then execute at cycle 5) CPI contribution: 3 cycles / 2 instructions = 1.5 stall per instruction

Control Hazards (Branch Misprediction)

Scenario: CPU fetches wrong code path, must flush pipeline

Cycle 1: BNZ r1, loop_start [IF] → [ID] → predict taken Cycles 2-15: Fetch from loop_start (14 stage pipeline filled) Cycle 15: Discover misprediction (branch actually not taken) Cycle 16: Flush all 14 stages, restart from correct path Stall: 14 cycles (entire pipeline depth) Frequency: 15% branches × 5% miss rate = 0.75% of instructions CPI contribution: 0.0075 × 14 = 0.105 cycles/instr

Memory Hazards (Cache Miss)

Scenario: Load instruction misses cache, must wait for DRAM

Load instruction: LOAD r1, [r2] L1 hit (95%): 4 cycles latency (in cache) L1 miss, L2 hit (4.75%): 10 cycles latency (L2 slower) L2 miss, L3 hit (0.2%): 100 cycles latency (L3 much slower) DRAM miss (0.05%): 200-300 cycles latency (main memory) Example: 20% loads in workload L1 hit: 0.20 × 0.95 × 4 = 0.76 cycles/instr L2 hit: 0.20 × 0.0475 × 10 = 0.095 cycles/instr L3 hit: 0.20 × 0.002 × 100 = 0.04 cycles/instr DRAM: 0.20 × 0.0005 × 250 = 0.025 cycles/instr Total: 0.92 cycles/instr (dominant stall!)

3. Instruction Classification

By Latency & Throughput

Instruction Latency Throughput CPI Impact
Integer ALU (ADD, XOR) 1 cycle 4/cycle (quad-issue) ~0 (ideal)
Integer Multiply (IMUL) 3-4 cycles 1/cycle (single) +2-3 if used next instr
FP Add/Sub 3-4 cycles 2/cycle +2-3 if dependent
FMA (Fused Multiply-Add) 4-5 cycles 2/cycle +3-4 if dependent
Load (L1 hit) 4 cycles 2/cycle +3 if used next
Load (L1 miss, L2 hit) 10 cycles 1/cycle +9 if used next
Branch (predicted correct) 0 cycles 1/cycle ~0 (no delay)
Branch (mispredicted) 14-20 cycles 0.5/cycle +14-20 (flush penalty)

By Memory Behavior

  • Compute-Bound: Bottleneck is CPU throughput (CPI ~0.8-1.2)
    • Example: Dense matrix math, tight loops, good cache hit rate
  • Memory-Bound: Bottleneck is cache misses (CPI ~2.0-4.0+)
    • Example: Database queries, pointer chasing, irregular access

4. Cache Behavior & Penalties

Cache Latency Hierarchy

L1 Cache: ~4 cycles, 32 KB, ~95% hit rate L2 Cache: ~10 cycles, 256 KB, ~90% hit rate (of L1 misses) L3 Cache: ~40 cycles, 8 MB, ~95% hit rate (of L2 misses) DRAM: ~200 cycles, unlimited, always hits Load Instruction Latency (from fetch to data ready): L1 hit: 4 cycles (data in L1) L2 hit: 10 cycles (L2 latency = 10, but pipeline started at 4, so wait 6 more) L3 hit: 100 cycles (need to fetch from L3) DRAM: 200-300 cycles (main memory access) Penalty (extra delay if result used next instruction): L1 hit: 0 cycles (no stall, forwarded from exec stage) L2 hit: 6 cycles (10 - 4 = gap between L2 and L1 latency) L3 hit: 36 cycles (40 - 4) DRAM: 196 cycles (200 - 4) CPI Impact Example (20% load instructions): Case 1 (95% L1 hit, 5% miss): = 0.20 × 0.95 × 0 + 0.20 × 0.05 × 6 = 0.06 cycles/instr Case 2 (70% L1 hit, 30% L2 hit, 5% miss): = 0.20 × 0.70 × 0 + 0.20 × 0.30 × 6 + 0.20 × 0.05 × 100 = 0 + 0.36 + 1.0 = 1.36 cycles/instr (much worse!)

Miss Rate Estimation

Working Set Size vs Cache Size:

If working set < cache size: ~95%+ hit rate (cold misses only) If working set ≈ cache size: ~90% hit rate (some evictions) If working set >> cache size: ~70-80% hit rate (thrashing) Example: Matrix multiply on 32×32 matrix Working set: 32 × 32 × 8 bytes = 8 KB L1 cache: 32 KB → 95%+ hit rate (fits!) Example: Matrix multiply on 1000×1000 matrix Working set: 1000 × 1000 × 8 bytes = 8 MB (or more with tiling) L1 cache: 32 KB → 50% hit rate (thrashing L1) L2 cache: 256 KB → 70% hit rate (fits partially) L3 cache: 8 MB → 90% hit rate (fits with room)

5. Performance Metrics & Measurements

Key Performance Counters

Metric Formula Target Interpretation
CPI Total Cycles / Total Instructions < 1.2 Lower is better (less time per instr)
IPC Total Instructions / Total Cycles > 0.8 Higher is better (more instr per cycle)
Throughput Frequency (GHz) / CPI > 2.8 GIPS Billion instr/sec (70% of peak)
Cache Hit Rate (Hits / Accesses) × 100% L1 > 95%, L2 > 90% Higher is better (fewer misses)
Memory Stall Rate (Memory Stall Cycles / Total) × 100% < 20% Lower is better (less memory wait)
Branch Accuracy (Correct Predictions / Branches) × 100% > 95% Higher is better (fewer flushes)

Experiment 1: Instruction Mix Impact on CPI

Objective: Understand how instruction composition affects performance.

Procedure:

  1. Run Workload 1: Integer Math (50% ALU, 20% MUL, 15% Load). Record CPI.
  2. Run Workload 2: GEMM (40% FMA, 30% Load). Record CPI.
  3. Calculate: How much does FMA latency increase CPI? (Compare: integer vs FMA)

Expected Result: GEMM has ~2× higher CPI (1.9 vs 0.8) due to FMA latency

Analysis: Why does 40% FMA cause more than 40% CPI increase?

Experiment 2: Cache Hit Rate Impact

Objective: Quantify how cache performance affects CPI.

Procedure:

  1. Select Workload 3: Database Query
  2. Set L1 Hit Rate to 95% (good cache). Record CPI.
  3. Lower L1 Hit Rate to 70% (poor cache). Record CPI.
  4. Calculate CPI increase: (CPI_poor - CPI_good) / CPI_good × 100%

Expected Result: Reducing cache hit rate from 95% to 70% increases CPI from ~3.0 to ~4.0 (+33%)

Analysis: How does memory stall rate change? Which matters more: L1 or L2?

Experiment 3: Branch Prediction Accuracy

Objective: Measure impact of branch mispredictions on CPI.

Procedure:

  1. Select Workload 4: Web Server (Branchy)
  2. Set Branch Accuracy to 95%. Record CPI.
  3. Lower to 85% (poor predictor). Record CPI.
  4. Calculate: CPI increase = (CPI_85% - CPI_95%) / CPI_95% × 100%

Expected Result: 10% misprediction rate increases CPI by ~15-20%

Analysis: Branchy code is sensitive to prediction quality. Why?

Experiment 4: CPU Frequency Scaling

Objective: Understand frequency vs CPI trade-off.

Procedure:

  1. Select any workload (e.g., Workload 6: Mixed)
  2. Set frequency to 2.5 GHz. Record throughput (GIPS), execution time.
  3. Increase frequency to 4.5 GHz. Record same metrics.
  4. Calculate speedup: Time_2.5GHz / Time_4.5GHz

Expected Result: Speedup ≈ 4.5 / 2.5 = 1.8× (CPI stays same, frequency increases)

💡 Tips & Troubleshooting

Understanding CPI Breakdown

  • High base CPI (>1.0): CPU pipeline stages add overhead. Consider simpler pipelines.
  • High RAW stalls (>0.2): Instruction dependencies limit ILP. Reorder code or use wider issue width.
  • High branch stalls (>0.1): Poor branch prediction. Improve predictor or restructure code (fewer branches).
  • High L1/L2 stalls (>0.5): Cache misses dominate. Improve working set size or access patterns (prefetching).

Optimizing for Better CPI

  • Reduce data dependencies: Unroll loops, use separate accumulators (more parallelism)
  • Improve cache locality: Tiling, row-major vs column-major, prefetching
  • Help branch prediction: Keep branches short, predictable conditions, avoid data-dependent branches
  • Use SIMD/vectorization: Process 4-8 elements per instruction (lower effective CPI)
  • Compiler optimizations: Loop unrolling, instruction reordering, prefetch insertion

Common Mistakes

  • Confusing CPI vs IPC: CPI = cycles/instr, IPC = instr/cycle (reciprocals)
  • Ignoring pipeline depth in branch penalty: Misprediction penalty ≈ pipeline depth (14-20 cycles, not constant)
  • Assuming cache misses independent: L1 miss → L2 miss → L3 miss cascade (not independent probabilities)
  • Forgetting superscalar base CPI: 4-issue superscalar has base CPI ~0.25, not 1.0!
  • Missing heterogeneous instruction latencies: ALU (1 cycle) vs FMA (4-5 cycles) vs Load (4-10 cycles) differ hugely

Real-World Example: TechCorp Optimization

Problem: Mixed workload (CPI 1.76) → Throughput only 2.0 GIPS (57% of 3.5 GHz peak)

Root Cause: Database queries (20% of time, CPI 3.6) are major bottleneck

Optimization Path:

  1. Improve L1 cache: Increase from 70% to 85% hit rate
    • Result: Query CPI drops from 3.6 to 2.8 → Overall CPI 1.60 (+9% improvement)
  2. Better branch prediction: Improve from 85% to 95% accuracy
    • Result: Query CPI drops to 2.5 → Overall CPI 1.48 (+7% improvement)
  3. Wider issue width: Upgrade to 6-issue superscalar
    • Result: All workloads benefit → Overall CPI drops to 0.9 (!) → Throughput 3.9 GIPS

Final Result: CPI 1.76 → 0.9 (50% reduction), Throughput 2.0 GIPS → 3.9 GIPS (2× speedup!)
