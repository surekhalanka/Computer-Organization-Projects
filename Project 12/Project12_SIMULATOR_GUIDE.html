📖 Core Concepts

1. Programmed I/O (PIO) vs Direct Memory Access (DMA)

PIO: The Old Way (Slow!)

CPU does ALL data transfer work: int pio_read(int disk_addr, void *mem_addr, int size) { write_to_disk_controller(CMD_READ, disk_addr); // Tell disk to read wait_for_disk_ready(); // Poll or interrupt for (int i = 0; i < size; i++) { char byte = read_from_disk_data_port(); // Read byte-by-byte memory[mem_addr + i] = byte; // Write to memory } return size; } Problems: - CPU BLOCKED during entire transfer - Must read every single byte from disk port - Must write every single byte to memory - Terrible for modern speeds (disk ~500 MB/s, CPU can do ~50 GB/s!) Example: Read 1 GB with PIO @ 3.5 GHz Time = 1,000,000,000 bytes × 10 cycles/byte ÷ 3.5 × 10^9 cycles/sec = 2.86 seconds of CPU doing NOTHING but I/O! CPU Utilization: 100% (not for computation, for data copying!)

DMA: The Smart Way (Fast!)

CPU initiates transfer, hardware does work: int dma_read(int disk_addr, void *mem_addr, int size) { dma_descriptor_t desc = { .src = disk_addr, .dst = mem_addr, .count = size }; write_dma_descriptor(&desc); // Tell DMA what to do (~1 μs CPU time) return size; // CPU RETURNS IMMEDIATELY! // ... CPU does other work (compute, serve queries) ... // ... Later, DMA sends interrupt when done ... } DMA controller handles: - Sending read command to disk - Waiting for disk latency - Reading data from disk buffer - Writing data to memory (via interconnect) - Sending completion interrupt Benefits: - CPU FREE for ~1-10 ms of transfer - Only ~1-5 μs CPU time per transfer (ISR) - CPU Utilization: <5% for I/O (95% available for queries!) Example: Read 1 GB with DMA @ 3.5 GHz DMA transfer: 1 GB ÷ 500 MB/s = 2 seconds Interrupts: 2 seconds ÷ 4 KB = 500,000 interrupts With coalescing (10 blocks/int): 50,000 interrupts CPU time: 50,000 × 4 μs = 200 ms = 0.2 seconds (0.6% CPU!) Speedup: 2.86 s (PIO) → 2.2 s (DMA) = 30% faster overall CPU freed: 2.86 s (PIO) → 0.2 s (DMA) = 93% CPU saved!

Why DMA Matters

Aspect PIO DMA
CPU Utilization (1 GB read) 100% blocked for 2.86 seconds < 1% for 2 seconds
CPU Parallelism 0 (no computation) Near 100% (full compute power)
Queries Served (100 queries/sec) ~0 queries during I/O ~200 queries (minimal stall)
Throughput (CPU + I/O) ~350 MB/s (CPU limits) ~500 MB/s (I/O throughput)
Implementation Complexity Simple (~10 lines) Moderate (DMA controller + interrupts)

2. DMA Architecture & Data Path

DMA Transfer Process (Step-by-Step)

DMA Transfer: 4 KB from SSD to Memory Step 1: CPU Setup (1-5 μs) - CPU writes DMA descriptor to DMA controller - Descriptor contains: source address, dest address, byte count - Example: read from SSD (sector 12345) to memory (0x80000000) Step 2: DMA Controller Queuing (< 1 μs) - DMA controller enqueues request in queue - If DMA busy, request waits (queue depth limits pending requests) Step 3: Disk Access (100-8000 μs depending on disk) - DMA sends read command to disk controller - CPU is FREE during this time! (Can process queries, etc.) - SSD: ~100 μs (fast, already positioned) - HDD: ~8000 μs (slow, need seek + rotational latency) Step 4: Data Transfer (~ 8-80 μs for 4 KB) - Disk controller receives data from media - DMA controller reads from disk buffer - DMA writes directly to main memory (via memory interconnect) - Size ÷ Bandwidth = Time 4 KB ÷ 500 MB/s = 8 μs (SSD) 4 KB ÷ 100 MB/s = 40 μs (HDD) Step 5: Completion Interrupt (1-10 μs) - DMA sends single interrupt to CPU (NOT per-byte!) - CPU wakes up, runs Interrupt Service Routine Step 6: ISR (Interrupt Service Routine) (1-5 μs CPU time) - CPU marks buffer as ready - Queues callback/wakeup event - Returns to previous task Total Time: 100-8000 μs (mostly disk latency, CPU free!) CPU Time: ~5 μs (just for setup + ISR) CPU Efficiency: 5 μs ÷ 8000 μs = 0.06% CPU (excellent!)

Multi-Channel DMA

Key Advantage: Multiple independent transfers simultaneously

8-Channel DMA Example (realistic modern system): Channels 0-3: Network NICs (2 × 10 Gbps) + Disk (NVMe) Channels 4-7: Additional Disks + Reserved Timeline (concurrent transfers): 0 μs: CPU initiates: - Channel 0: Read 10 MB from Disk 0 to buffer A - Channel 1: Write 5 MB from buffer B to Disk 1 - Channel 2: Receive 2 MB packet from NIC (All 3 happen in PARALLEL!) 100 μs: Channel 2 completes packet (fast network) └─ Sends interrupt, CPU processes network data └─ Meanwhile, channels 0 & 1 still transferring! 10 ms: Channel 0 completes disk read └─ Sends interrupt └─ Channel 1 still writing (overlapped!) 15 ms: Channel 1 completes disk write └─ All transfers done Sequential (without DMA): 0-100 μs: Receive network (NIC) 100-10100: Read disk 0 (waits for network done) 10100-15100: Write disk 1 (waits for disk 0 done) Total: 15 ms (everything BLOCKED on each other!) With DMA: Total: max(100, 10000, 15000) = 15 ms BUT! CPU free the ENTIRE time! AND! Better with fewer large blocks (Disk 0 + 1 can be concurrent too)

3. Interrupt Handling & Overhead

Interrupt Service Routine (ISR) Latency Breakdown

Phase Time (μs) Why This Happens
1. Interrupt Signal ~0.1-0.5 DMA → CPU signaling (electrical delay)
2. Pipeline Flush ~0.5-2.0 CPU stops current work, drains 14-20 stage pipeline
3. Context Save (registers) ~0.5-1.0 Push IP, flags, RAX, RBX, etc. to stack
4. ISR Dispatch ~0.1-0.2 Lookup interrupt handler, jump to code
5. ISR Execution ~0.5-2.0 Mark buffer, queue callbacks (actual work)
6. Context Restore ~0.5-1.0 Pop registers, return to interrupted task
TOTAL ISR LATENCY ~3-7 (typically 4) All phases combined

Interrupt Coalescing (Crucial Optimization!)

Problem: Too Many Interrupts!
Example: 10 Gbps network @ 1500-byte frames Frames/sec = 10 Gbps ÷ (1500 bytes × 8 bits/byte) = 10,000,000,000 ÷ 12,000 = 833,333 frames/sec If 1 interrupt per frame: CPU overhead = 833,333 frames/sec × 4 μs/interrupt = 3,333 ms/sec = 333% (!!) CPU: Can't handle this many interrupts! Result: Packet loss, network stalls, system collapse Solution: Coalesce multiple completions into 1 interrupt With Coalescing Factor = 10: Actual interrupts = 833,333 ÷ 10 = 83,333 /sec CPU overhead = 83,333 × 4 μs = 333 ms/sec = 33% Still high, increase to 100: Actual interrupts = 8,333 /sec CPU overhead = 8,333 × 4 μs = 33 ms/sec = 3.3% This is acceptable! Trade-off: - No coalescing: Lower latency (each transfer notified immediately) - Coalesce 10: Latency +40 μs, CPU -300% - Coalesce 100: Latency +400 μs, CPU -330% Best practice: Coalesce 10-50 blocks (balance latency vs CPU)

4. DMA Efficiency Metrics

Key Performance Indicators

Metric Definition Formula Good vs Bad
DMA Efficiency % of time actually transferring Transfer time ÷ Total time × 100% >90% good, <70% investigate
Transfer Latency Time from request to data ready Disk latency + Transfer time + ISR <100 μs excellent, >1 ms poor
Interrupt Overhead % CPU time in ISR (Interrupts/sec × ISR time) × 100% <5% good, >20% bottleneck
Memory BW Utilization % of available interconnect used (Actual MB/s ÷ Peak MB/s) × 100% <80% good (headroom), >90% saturated
Queue Depth Avg pending I/O requests Total requests in flight 4-16 balanced, <2 underutilized, >32 risky

Calculating DMA Efficiency

Example: 100 MB transfer from 500 MB/s SSD Transfer time = 100 MB ÷ 500 MB/s = 200 ms (actual data movement) Disk latency = 100 μs (seek + read head position) Interrupt overhead (coalescing 10, 100 MB ÷ 4 KB = 25,000 blocks): Interrupts = 25,000 ÷ 10 = 2,500 Interrupt time = 2,500 × 4 μs = 10 ms Queue wait = ~5 ms (if other DMA requests active) Total time = 100 μs + 200 ms + 10 ms + 5 ms = 215 ms DMA Efficiency = 200 ms ÷ 215 ms × 100% = 93% Interpretation: - 93% of time is actual data transfer (good!) - 5% waiting in queue - 2% other overheads To improve: - Increase coalescing factor (reduce interrupt overhead) - Use multi-channel DMA (reduce queue wait) - Or, transfer is not bottleneck - check disk/network instead

5. Bottleneck Analysis

Finding What Limits Performance

Bottleneck Symptoms Solution
Disk Latency Disk latency time > 50% of total time Use faster storage (SSD vs HDD), prefetch, caching
Interrupt Overhead CPU overhead > 10%, many small transfers Increase coalescing factor, larger blocks
Memory Bandwidth BW utilization > 90%, other traffic on system Add memory channels, reduce other I/O, prioritize
Queue Saturation Avg queue depth near max, requests delayed Add DMA channels, increase queue depth, prioritize
CPU Stalls (Context Switch) ISR interrupts processing frequently Use threaded ISR, defer interrupt processing

🧪 Lab Experiments (Hands-On)

Experiment 1: PIO vs DMA Performance

Objective: Quantify the speedup from using DMA.

Procedure:

  1. Run Workload 1: Sequential SSD Read (100 MB)
  2. Note CPU overhead % and throughput
  3. Manually calculate PIO time: 100 MB × 10 cycles/byte ÷ 3.5 GHz
  4. Compare: PIO time vs DMA time

Expected Result: DMA is ~10-30× faster in CPU utilization (0.1% vs 3%)

Experiment 2: Interrupt Coalescing Impact

Objective: Measure CPU overhead reduction with coalescing.

Procedure:

  1. Run Workload 3: Network I/O
  2. Set coalescing to 1. Record CPU overhead %
  3. Increase to 10, then 50, then 100. Record each
  4. Plot: Coalescing factor (x) vs CPU overhead (y)

Expected Result: CPU overhead drops ~90% when going 1→100 coalescing

Experiment 3: DMA Channels vs Throughput

Objective: Understand multi-channel parallelism.

Procedure:

  1. Run Workload 4: Mixed Disk + Network
  2. Set DMA channels to 1. Record throughput, queue depth
  3. Increase to 2, 4, 8. Record metrics each time
  4. Calculate: Throughput scaling efficiency

Expected Result: Throughput should scale ~linearly up to 4-8 channels

Experiment 4: Block Size Effect on Efficiency

Objective: Optimize block size for DMA transfers.

Procedure:

  1. Run Workload 1: Sequential SSD
  2. Set block size to 4 KB. Record efficiency, interrupt rate
  3. Increase to 16 KB, 64 KB, 256 KB. Record each
  4. Find optimal block size

Expected Result: Efficiency improves (fewer interrupts) with larger blocks, but latency increases

Experiment 5: Sequential vs Random I/O

Objective: Compare DMA efficiency for different access patterns.

Procedure:

  1. Run Workload 1: Sequential SSD. Record: latency, throughput, efficiency
  2. Run Workload 2: Random HDD. Record same metrics
  3. Compare: How does disk latency affect overall performance?

Expected Result: Random access has much higher latency (8000 vs 100 μs), but DMA still helps (CPU free!)

Experiment 6: Memory Bandwidth Saturation

Objective: Understand interconnect limits.

Procedure:

  1. Run any workload (Workload 5: Burst Write is good)
  2. Record memory BW utilization %
  3. Lower available memory BW in settings (from 100 GB/s to 50 GB/s)
  4. Re-run. How much does throughput drop?

Expected Result: Throughput stays same (disk throughput is limit), but utilization % rises; if BW really is limit, throughput drops

💡 Tips & Troubleshooting

Understanding DMA Efficiency

  • High disk latency (HDD) → Efficiency appears low, but CPU is FREE! Not necessarily bad.
  • High interrupt rate → Reduce block size or increase coalescing
  • Memory bandwidth bottleneck → Consider NVMe over HDD, or prioritize critical transfers
  • Low queue depth → More DMA channels or concurrent transfers needed

Real-World Optimization Checklist

  • ✓ Enable DMA (never use PIO for bulk transfers)
  • ✓ Set appropriate coalescing (10-50 blocks typical)
  • ✓ Use large blocks when possible (64 KB+ reduces interrupts)
  • ✓ Multiple DMA channels (at least 4 for modern systems)
  • ✓ Queue depth ≥ 8 (prevent stalls)
  • ✓ Monitor memory bandwidth (should be <80% utilized)
  • ✓ Test with realistic workloads (mixed sequential + random)

Common Mistakes

  • Confusing efficiency with speed: Low efficiency (30%) with HDD just means disk is slow. DMA still freed CPU!
  • No coalescing: Leads to 1000+ interrupts/sec, CPU spends more time in ISR than transferring
  • Block size too small: 512 B blocks on 10 Gbps network = 20,000 interrupts/sec!
  • Ignoring memory bandwidth: Multiple DMA channels compete for interconnect; can saturate at >90%
  • Assuming DMA has no overhead: Interrupt handling is not free (~5 μs per interrupt)

Real-World Example: StorageFlow Optimization

Problem: Database server with 10 Gbps network, but only 2 GIPS throughput (20% of potential)

Root Cause (Investigation):

  1. Run simulation with: Sequential SSD read, 100 MB, default settings
  2. Discover: CPU overhead 8%, interrupt rate 125,000/sec (too high!)
  3. Secondary: Memory BW only 50% utilized (headroom available)

Optimization Path:

  1. Increase coalescing: 1 → 10
    • Result: CPU overhead 8% → 1.2%, interrupt rate 12,500/sec
  2. Larger block size: 4 KB → 64 KB
    • Result: CPU overhead 1.2% → 0.3%, throughput +15%
  3. More DMA channels: 2 → 8
    • Result: Throughput +40% (parallel transfers)

Final Result: CPU overhead 8% → 0.3%, Throughput 2 GIPS → 3.5 GIPS (1.75× speedup!)
